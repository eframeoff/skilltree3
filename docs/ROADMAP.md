# SkillTree — план работ

Дерево навыков — сердце продукта. И конструктор (для тренера), и обучение по нему
(для ученика) должны быть одинаково удобны для **любого** навыка: кондитер,
музыкант, художник, футбольный или киберспортивный тренер сами решают, чему и как
учить, как принимать зачёты (видео / фото / текст / очно) и как фиксировать
достижения учеников.

**Принцип плана: модель вперёд.** Почти всё упирается в три перегруженные
структуры — `type` узла, плоское `video`, единственный `coachId` / `authorId`.
Пока они не расщеплены, любая фича пишется как костыль. Поэтому Фаза 0 невидима,
но разблокирует остальное.

## Зафиксированные продуктовые решения
1. **Авторитет наставника — выводимый**: сдал узел/ветку на ≥4★ → кандидат,
   плюс тумблер делегирования от тренера. Не назначаем поимённо.
2. **Финальность делегированной оценки — по-разному**, настраивается на узле:
   практики — финал с аудитом; зачёты — `provisional` → подтверждает тренер.
3. **Граница делегирования — флаг на каждом узле** (`delegation.delegable`).
4. **Со-тренеры — два пути**: добавить при создании дерева ИЛИ пригласить как
   ученика и повысить до тренера.

## Порядок реализации
Зависимости: **Ф0 → всё**. Ф5 требует Ф0 (reviewers, reviewerId, delegation).
Ф6 требует Ф0 (версионирование). Ф1–Ф4 параллелятся после Ф0.
Рекомендованный порядок по ценности: **0 → 1 → 5 → 3 → 2 → 4 → 6**.

## Фаза 0 — Фундамент модели и стора (без новых экранов) ✅ СДЕЛАНО

Цель: расщепить перегруженные сущности, сохранив обратную совместимость —
старые деревья продолжают рендериться без ручной переписки.

> **Статус.** Модель/стор расщеплены, сборка зелёная, регрессий нет (`type`
> сохранён как derived — экраны читают его до Phase 1). Сделано: оси узла +
> `migrateNode`/`migrateTree` + хелперы (`shapeKey`, `isBoss`, `isVideoNode`,
> `gradeMode`, `submitKinds`, `isLiveNode`); `parts[]`/`createdAt`/`reviewerId`/
> `provisional` в попытках; `attestLive`; `reviewers[]` на записи + `addReviewer`/
> `removeReviewer` + `videosForCoach` маршрутит по ревьюерам; `collaborators`/
> `gating` на дереве + `treeSnapshot`/`publishTreeUpdate`/`addCollaborator`;
> ветка `gating:'graph'` в `recomputeProgress`.
> **Отложено намеренно:** переключение read-path учеников на `published`-снимок —
> вместе с UI «Опубликовать обновление» в Фазе 6 (данные/функция уже готовы).

### Модель узла (`src/data/treeUtils.js`) — `type` → три оси
```js
node = {
  id, title, level, x, y, prereqs, optional, group?,
  teach:  { blocks: [{ kind:'video|photo|text|audio|file', payload }] }, // заменяет fake-видео + steps
  submit: { kinds:['video|photo|text|audio|file|live|none'], min:1 },     // что присылает ученик
  grade:  { mode:'auto-quiz|pass-fail|stars-5|rubric', quiz?, rubric? },
  delegation: { delegable:false, mode:'provisional' },                    // решения #2, #3
}
```
- `shapeKey(node)` выводит форму из `grade.mode` + `submit` (звёзды-зачёт = гекс),
  чтобы `SkillNode.jsx` и `EditorCanvas.jsx` не знали о старом `type`.
- `migrateNode(legacy)` маппит `test/practice/exam` в новые оси — деревья
  `src/data/trees/*` не переписываем руками.

### Модель попытки (`src/data/users.js`, стор)
Добавить: `parts:[{kind,payload}]`, `reviewerId`, `reviewerRole`, `createdAt`,
`provisional`. Разом даёт комбо-сдачу, таймлайн и провенанс делегирования.

### Запись ученика (`src/data/users.js`)
`coachId` → `reviewers:[{ userId, role, scope:{ levels|branchRootIds|nodeIds } }]`.
`coachId` оставить как геттер «primary» для совместимости.
`videosForCoach` (`StoreContext.jsx`) уже маршрутизирует по записям — расширяем
на список ревьюеров.

### Дерево
`collaborators:[{ userId, role:'co-author|co-coach' }]`, `gating:'levels'|'graph'`,
и **версионирование** — рабочий черновик (`nodes`) против опубликованного снимка
(`published`); ученики читают снимок. Закрывает «правку живого дерева» и нужна
для со-тренеров.

### Стор (`src/context/StoreContext.jsx`)
- `acceptVideo(id, stars, reviewerId)` пишет `reviewerId` / `provisional` в факт.
- Новые: `attestLive(...)`, `publishTreeUpdate(treeId)` со снимком.

**Критерий приёмки:** существующие три дерева и весь сид-прогресс работают без
изменений; прохождение/проверка/публикация — без регрессий.

## Фаза 7 — Медиа и хранилище (надстройка, подключается с Фазы 1)

Решение и обоснование: [docs/adr/0001-media-storage.md](adr/0001-media-storage.md).
Сейчас видео — мок (`VideoPlayerPlaceholder`, `thumb` = цвет), хранилища нет —
поле чистое.

**Принцип: два слоя, которые не путаются.**

### Слой 1 — Хранилище сдач (обязательное, приватное, наше)
Ядро LMS: тренер обязан видеть именно ту попытку, которую оценивал; её нельзя
терять при удалении соцсетью. Соцсети — это API публикации, не файловый хостинг.
- Object storage **Cloudflare R2** (нулевой egress) для фото/файлов;
  **Cloudflare Stream / Mux / Bunny** для видео (транскод + адаптив + превью).
- **Прямая загрузка по presigned-URL**: файл из браузера ученика идёт в
  хранилище мимо app-сервера.
- **Подписанные ссылки на просмотр** для тренера/наставника.
- **Ярусное хранение**: одобренные зачёты и featured — долго; отклонённые
  черновики авто-удаляются через N дней (ложится на логику «лучшая попытка»).
- Клиентское сжатие перед загрузкой.

### Слой 2 — Соцсети как маркетинг (opt-in, поверх)
Виральность как надстройка над уже одобренным контентом, не как хранилище.
- Привязка аккаунта ученика (TikTok / Instagram / YouTube).
- «Поделиться» доступно только для **одобренных** клипов из подборки
  (`is_featured` / `compilation_ready` уже в модели).
- Best-effort чтение публичных метрик (лайки) привязанного клипа → лидерборд/
  подборка. Зависит от публичности и API — не критический путь.

### Связь с моделью (`parts[]` из Ф0)
Добавить два вида part и `'link'`/`'embed'` в `submit.kinds`:
```js
{ kind:'video', payload:{ storageKey, playbackUrl, thumb, duration } } // хостим мы
{ kind:'embed', payload:{ provider:'tiktok|instagram|youtube', url, thumb } } // хостит соцсеть
```
- Ученик может приложить внешнюю ссылку (нам ноль хранения, ему соц-пруф);
  тренер смотрит во встроенном плеере.
- **Высокие ставки (зачёт-гексагон) требуют хостимую копию** — её нельзя удалить
  задним числом. Практики можно принимать по `embed`. Это per-node политика
  в духе `delegation` / `grade`.
