# ADR 0002 — Бэкенд и персистентность

- **Статус:** принято (поэтапно)
- **Дата:** 2026-06-16
- **Связано:** [docs/ROADMAP.md](../ROADMAP.md) (Фаза Б), [ADR 0001](0001-media-storage.md)

## Контекст

Сейчас всё состояние живёт в памяти React (`StoreContext` на `useState` + сид-данные
в JS). Модель намеренно plain-serializable (принцип из `CLAUDE.md`). Вопрос: нужна
ли БД и поднимать ли её заранее.

Ограничение: модель ещё активно меняется (Фазы 1, 5, 6 — `parts`, делегирование,
`reviewers`, `collaborators`, версионирование). Замораживать схему сейчас —
преждевременно.

## Решение

Поэтапно, без преждевременной БД.

1. **Сейчас — персистентность через `localStorage`** (`src/hooks/usePersistentState.js`).
   Состояние переживает перезагрузку; модель проверяется на сериализуемость рано.
   Версионируется (`VERSION`) — при смене формы сидов старые данные сбрасываются.
2. **Целевой стек — Supabase** (Postgres + Auth + Storage). Обоснование:
   - данные реляционные (деревья, узлы, уровни, записи, прогресс-факты, попытки,
     ревьюеры, коллабораторы, сообщения) → Postgres;
   - встроенная авторизация ложится на существующий `AuthContext`;
   - Storage + signed URLs закрывают [ADR 0001](0001-media-storage.md) по медиа;
   - RLS даёт разграничение доступа (ученик / наставник / тренер) без ручного бэкенда.
3. **Когда поднимать реальную БД (триггер):** появление мультипользовательности с
   реальными данными — разные устройства, настоящая авторизация, загрузка файлов.
   Это Фазы 5–6 (наставники, со-тренеры) и обязательно **до Фазы 7** (медиа).

## Принцип, который это удерживает

Формы данных, стабилизируемые в Фазах 0–1, **и есть будущая схема БД**. Перевод в
таблицы — почти механический. Поэтому лучшая подготовка к БД — держать модель
чистой, сериализуемой и хранить только факты (производное — выводить), что уже
делается (`recomputeProgress`).

## Последствия

- Свопнуть бэкенд — локальное изменение за `StoreContext` (read/write API уже
  спроектированы API-образно).
- `localStorage` — временно; при переходе на Supabase станет кэшем/офлайн-слоем
  либо убирается.
- Схему фиксируем не раньше, чем устаканятся Фазы 1/5/6.

## Альтернативы (отклонены сейчас)

- **Поднять полную БД немедленно** — миграции на каждую фазу, преждевременно.
- **Свой бэкенд на Node/Express** — больше работы, чем даёт Supabase BaaS на
  текущем этапе.
- **Firebase** — жизнеспособен, но данные реляционные; Postgres/Supabase точнее
  ложатся на модель и на медиа-ADR.
